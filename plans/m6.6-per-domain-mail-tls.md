# M6.6 — Per-Domain Mail TLS

**Status:** draft blueprint  
**Branch (target):** `m6.6/per-domain-mail-tls`  
**ADR target:** ADR-0091 — per-domain mail SAN provisioning  
**Supersedes/Updates:** ADR-0048 (M6.4 panel-hostname-only mail) is partially relaxed: panel-hostname stays the canonical default, per-domain SAN becomes opt-in per tenant domain that enables email.

---

## Background

GH #133 surfaced a real UX gap. Today a tenant with mailboxes at `you@brand.com` has to point their mail client at `mail.<panel-hostname>` because that's the only name on the cert Stalwart serves. Connecting to `mail.brand.com` :465 returns Stalwart's bootstrap self-signed (SNI miss).

M6.4 made `mail.<panel-hostname>` the canonical default. That choice was right for shared-host quickstart (no per-domain cert juggling, no rate-limit math). It's wrong as the **only** option: cPanel, DirectAdmin, Hestia, Mailcow all auto-issue per-domain mail certs and users expect that to work.

## Goal

When a tenant domain enables email, the panel obtains an LE cert covering:

- `mail.<domain>`
- `autoconfig.<domain>` (Thunderbird autodiscover)
- `autodiscover.<domain>` (Outlook autodiscover)
- `mta-sts.<domain>` (MTA-STS HTTPS policy fetch)

That cert is deployed into Stalwart's `x:Certificate` registry; Stalwart serves it on the matching SNI for ports 25 (STARTTLS), 465, 587, 993. Panel-hostname stays the global default cert for connections without SNI or matching no per-domain cert.

## Non-Goals

- DNS-01 challenge support — HTTP-01 via the existing nginx `:80` ACME location stays the only challenge method. Domains without HTTP-01 reachability stay on the panel-hostname mail cert.
- DKIM/DMARC/SPF DNS records — out of scope. M6.5 already wired DKIM key per domain via Stalwart Domain/set.
- Wildcard certs — single-SAN-per-cert keeps the LE rate-limit calculation simple.

## Constraints to budget for

1. **LE registered-domain rate limit: 50 new orders / week / registered domain.**  
   Adding 1 mail cert per tenant domain is well under that for a single panel (typical operator: 10-100 domains). But `brand.com` + `mail.brand.com` + `autoconfig.brand.com` + `mta-sts.brand.com` + `autodiscover.brand.com` all share `brand.com` as registered-domain. Each new domain order counts. Stay under 50/week.
2. **HTTP-01 needs DNS to resolve.** `mail.<domain>` etc must have an A record pointing at the panel before issuance. Pre-flight DNS check + skip if missing + retry on next reconcile.
3. **Renewal cadence.** Existing panel-hostname cert renewal already runs via certbot's renewal timer + our deploy-hook. Per-domain certs join the same timer; deploy-hook gets fanout logic.
4. **Failure → fallback.** A cert failure for one domain MUST NOT break mail for other domains. Stalwart already falls back to the default cert on SNI miss; the panel UI surfaces the failure.

## Architecture

### Cert lifecycle (per domain)

```
domain.email_enable
    → DB: mail_certificate row (status=pending)
    → reconciler: ssl.mail.issue (new agent verb)
        → DNS check (mail/autoconfig/mta-sts/autodiscover.<domain> all A-record → panel-public-IP)
        → certbot certonly --webroot --domains mail.<d>,autoconfig.<d>,mta-sts.<d>,autodiscover.<d>
        → on success: JABALI_PANEL_CERT_KIND=mail-domain RENEWED_LINEAGE=/etc/letsencrypt/live/mail.<d> \
            /etc/letsencrypt/renewal-hooks/deploy/jabali-panel-cert.sh
        → row status=issued
    → on failure: row status=failed, last_error populated, next reconciler tick re-evaluates
```

### Stalwart Certificate registry

Each per-domain cert lives as a named `x:Certificate` entry keyed by domain ID:

```json
{
  "@type": "create",
  "object": "x:Certificate",
  "value": {
    "domain-<ulid>": {
      "certificate": {"@type":"Text","value":"<PEM>"},
      "privateKey":  {"@type":"Text","secret":"<PEM>"}
    }
  }
}
```

Stalwart's SNI matcher extracts SANs from the cert and routes accordingly. Default cert stays `#panel-mail` (M6.4).

### DB

```sql
CREATE TABLE mail_certificate (
  id              CHAR(26) PRIMARY KEY,
  domain_id       CHAR(26) NOT NULL,
  lineage_path    VARCHAR(255) NOT NULL,
  status          VARCHAR(32) NOT NULL DEFAULT 'pending',
  last_error      TEXT NULL,
  issued_at       TIMESTAMP NULL,
  expires_at      TIMESTAMP NULL,
  created_at      TIMESTAMP NOT NULL DEFAULT CURRENT_TIMESTAMP,
  updated_at      TIMESTAMP NOT NULL DEFAULT CURRENT_TIMESTAMP ON UPDATE CURRENT_TIMESTAMP,
  UNIQUE KEY (domain_id),
  CONSTRAINT fk_mailcert_domain FOREIGN KEY (domain_id) REFERENCES domains(id) ON DELETE CASCADE
);
```

`status ∈ {pending, dns_missing, issuing, issued, failed, deleted}`.

### Reconciler

New phase `reconcileMailCerts` runs after `reconcileMailSettings`. For each domain with `email_enabled=1`:

- Ensure a `mail_certificate` row exists (lazy create).
- If `status=pending` → dispatch `ssl.mail.issue`.
- If `status=issued` AND `expires_at < now + 30d` → dispatch `ssl.mail.renew`.
- If `status=dns_missing` → re-check DNS once per hour; promote to pending when A records present.
- If `status=failed` → backoff 3h before retry.

### Agent verbs

- `ssl.mail.issue { domain_id, domain_name }` — DNS check + certbot issue + deploy-hook + return `{ lineage_path, expires_at }`.
- `ssl.mail.renew { domain_id, domain_name }` — certbot renew --cert-name + deploy-hook.
- `ssl.mail.delete { domain_id }` — remove the Stalwart `x:Certificate` entry + (optional) certbot revoke.

Deploy-hook `jabali-panel-cert.sh` gains a third `kind=mail-domain` branch that calls `jabali-stalwart-push-cert --name domain-<ulid> --cert <path> --key <path>` instead of writing `/etc/jabali/tls/panel-mail.*`.

### UI

- Domain settings → Mail tab → new "Mail TLS" section.
- Status chip (pending / issuing / issued / dns_missing / failed) + DNS A-record table (mail/autoconfig/mta-sts/autodiscover.<domain> → expected vs observed).
- "Re-issue" button for failed/expired.
- "Use panel-hostname cert instead" toggle — opt out of per-domain (fallback to current M6.4 behavior).

## Steps

1. **Migration + model.** Add `mail_certificate` table + GORM model + repository.
2. **Agent verb skeleton.** `ssl.mail.issue` returns dns_missing immediately for any domain without A records on the 4 SANs. Wire a contract test.
3. **certbot integration.** Real `ssl.mail.issue` calls `certbot certonly --webroot -d mail.<d> -d autoconfig.<d> -d mta-sts.<d> -d autodiscover.<d>`. Lineage at `/etc/letsencrypt/live/mail.<d>/`.
4. **Deploy-hook extension.** New `kind=mail-domain` branch in `jabali-panel-cert.sh` + matching `--name` arg on `jabali-stalwart-push-cert`. Idempotent re-push (primaryKeyViolation = success).
5. **Reconciler phase.** `reconcileMailCerts` with the state machine above; backoff + DNS re-check timers.
6. **UI: Mail TLS section.** Status + DNS table + Re-issue + opt-out toggle. Mirror DomainSSLSection styling.
7. **Rate-limit guard.** Per-panel counter of LE orders/week; block + UI warn when nearing 40/week. Operators can request rate-limit increase via LE form.
8. **E2E + runbook.** Playwright: enable email → wait for issued → curl `openssl s_client -servername mail.<d>` returns LE cert. Runbook covers force-reissue + revoke.
9. **ADR-0091.** Document the per-domain SAN scheme + LE rate-limit math + Stalwart Certificate registry naming + deploy-hook fanout.

## Rate-limit math

Per LE: 50 certificates per registered domain per week. Our per-domain order = 1 cert covering 4 SANs (mail/autoconfig/mta-sts/autodiscover). So each tenant domain consumes 1 order. A single panel with 50 tenant domains hits the limit in 1 week ONLY if every domain enabled mail in the same 7-day window — unrealistic for shared hosting. For multi-tenant panels exceeding that, operator requests a rate-limit increase per the LE process.

Renewal does NOT count against new-orders limit (LE's renewal-exemption rule on identical SAN sets).

## Open questions

- **Per-domain autodiscover XML.** mta-sts policy file is hosted on `https://mta-sts.<domain>/.well-known/mta-sts.txt`. nginx vhost needs a per-domain `mta-sts` server block when this cert lands. Probably belongs to a follow-up M6.7 (autodiscover endpoints), NOT M6.6. M6.6 just gets the cert.
- **Wildcard option for big-multi-tenant.** Operators with 100s of domains may prefer a wildcard `*.<panel-hostname>` cert covering `mail.X.<panel-hostname>` synonyms. Out of scope; document the workaround.
- **DKIM record DNS auto-publish.** Already in M6.5 scope. Reuse the per-domain DNS-management hooks here for the A-record creation.
